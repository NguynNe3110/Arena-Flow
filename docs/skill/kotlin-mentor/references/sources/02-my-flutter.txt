# PHẦN 2. KIẾN THỨC DART ĐÃ TỪNG THẢO LUẬN

Đây là nhóm kiến thức ngôn ngữ đã có những cuộc thảo luận cụ thể.

## 2.1. Generic trong Dart

Đây là một trong những chủ đề người học đã hỏi khá sâu.

Các nội dung đã thảo luận:

- Generic type: `<T>`, `<A, B>`.
- Generic class và generic function.
- Type parameter.
- Type argument.
- Generic constraint với `extends`.
- Subtype và supertype.
- Generic kết hợp với Future.
- Generic trong BaseBloc, UseCase, Repository và Result.

Ví dụ:

```dart
Future<T?> push<T extends Object?>(...)
```

Người học đã tìm hiểu:
- `T` là một type parameter, đại diện cho kiểu dữ liệu sẽ được xác định khi sử dụng.
- `Object?` là kiểu giới hạn cho `T`.
- `extends` trong generic là constraint, không phải cứ xuất hiện là đang tạo một class con.
- Khi gọi với các kiểu khác nhau, kiểu trả về cũng thay đổi tương ứng.

Ví dụ:

```dart
Future<String?> result1;
Future<User?> result2;
Future<int?> result3;
```

Đã phân biệt:
- `Future<T>` là Future chứa kết quả kiểu T.
- `func<T>()` là function có generic type parameter.
- Dart có thể tự suy luận generic type argument trong nhiều trường hợp.

### Generic trong kiến trúc BLoC

Đã thảo luận:

```dart
BaseBloc<
  E extends BaseBlocEvent,
  S extends BaseBlocState
>
```

Người học đã hiểu mục đích của constraint:

- E phải thuộc nhóm event hợp lệ.
- S phải thuộc nhóm state hợp lệ.
- Không thể tùy ý truyền String, int vào vị trí yêu cầu Event và State.
- Constraint giúp kiểm tra tính hợp lệ của kiểu dữ liệu khi sử dụng generic class.

## 2.2. extends và with

Đã tìm hiểu sự khác nhau giữa hai cơ chế.

### extends

Dùng để kế thừa một class.

### with

Dùng để kết hợp mixin nhằm tái sử dụng hành vi.

Đã làm rõ:
- Mixin không phải một instance độc lập được tạo ra để sử dụng như object thông thường.
- Mixin cho phép nhiều class tái sử dụng cùng một hành vi.
- Mixin có thể sử dụng `on` để giới hạn loại class được phép kết hợp.

Ví dụ:

```dart
class User {}

mixin Logger on User {
  void log() {
    print('Logging...');
  }
}

class Admin extends User with Logger {}
```

### Liên hệ Freezed

Người học từng gặp:

```dart
class AppEvent with _$AppEvent
```

Đã được giải thích rằng `_$AppEvent` là phần code được Freezed generate, sử dụng cơ chế mixin của Dart. Đây không phải cú pháp riêng của BLoC.

## 2.3. Factory constructor và Freezed

Đã thảo luận thông qua ví dụ khai báo route:

```dart
@freezed
class AppRouteInfo with _$AppRouteInfo {
  const factory AppRouteInfo.login() = _Login;

  const factory AppRouteInfo.main() = _Main;

  const factory AppRouteInfo.itemDetail(User user)
      = _UserDetail;
}
```

Các vấn đề đã được làm rõ:

- `factory` là constructor đặc biệt của Dart.
- Factory constructor không nhất thiết phải tạo instance trực tiếp bằng constructor thông thường.
- Freezed sử dụng factory constructor làm điểm khai báo các biến thể của union/sealed model.
- Freezed generate những implementation như `_Login`, `_Main`, `_UserDetail`.
- `itemDetail(User user)` thể hiện route cần truyền dữ liệu.
- `login()` và `main()` không cần tham số.

Người học từng có suy nghĩ rằng factory chính là thao tác tạo subclass. Đã được làm rõ: việc sinh các subclass implementation là công việc của Freezed code generation; factory là cơ chế constructor được sử dụng để tạo/trả về những implementation đó.

## 2.4. Spread operator (...)

Đã hỏi và tìm hiểu toán tử `...` trong Dart.

Cần tiếp tục củng cố:
- Spread operator dùng để trải các phần tử của một iterable hoặc map vào collection khác.
- Null-aware spread `...?`.
- Phân biệt spread với việc thêm nguyên một collection thành một phần tử.

## 2.5. Map<String, dynamic>

Đã thảo luận trong quá trình làm việc với Supabase và DTO.

Đã hiểu:
- `Map` lưu dữ liệu theo dạng key-value.
- `String` là kiểu của key.
- `dynamic` cho phép value có nhiều kiểu dữ liệu.
- Thường được sử dụng để biểu diễn JSON hoặc payload gửi đến backend.

Ví dụ:

```dart
final Map<String, dynamic> payload = {
  'user_id': '123',
  'quantity': 10,
  'is_active': true,
};
```

Người học hiểu Map là cấu trúc dữ liệu trung gian ở Data Layer, không nên để định dạng dữ liệu của backend ảnh hưởng trực tiếp đến Domain Entity.

# PHẦN 3. FLUTTER BLOC

Đây là một trong những phần kiến trúc người học đã dành nhiều thời gian tìm hiểu.

Người học từng tiếp cận một dự án Flutter sử dụng kiến trúc BLoC có Base/Common/Feature.

## 3.1. Luồng hoạt động cơ bản

Đã tìm hiểu luồng:

UI → BLoC → UseCase/Repository → DataSource → API/Database

Khi dữ liệu trả về:

DataSource → Repository → UseCase → BLoC → State → UI

Các nguyên tắc đã được xác định:

- UI không trực tiếp gọi API.
- BLoC không trực tiếp gọi DataSource.
- BLoC chịu trách nhiệm xử lý Event và phát State.
- Repository che giấu nguồn dữ liệu.
- Domain không phụ thuộc vào Data implementation.

## 3.2. Event và State

Người học đã tiếp cận mô hình:

Event → Bloc → State

Trong đó:

**Event**
- Đại diện cho hành động hoặc yêu cầu xử lý.
- Được gửi từ UI đến BLoC.
- Ví dụ: LoginRequested, LoadUsers, DeleteUser.

**State**
- Đại diện cho trạng thái hiện tại của màn hình.
- Được UI lắng nghe để render.
- Ví dụ: Initial, Loading, Success, Error.

Đã tìm hiểu cách tổ chức Event và State riêng biệt thay vì nhồi toàn bộ logic vào UI.

## 3.3. BlocBuilder, BlocListener và BlocConsumer

Đây là nội dung đã được giải thích tương đối rõ.

### BlocBuilder

Nhiệm vụ: lắng nghe State và rebuild UI khi State thay đổi.

Tương tự việc UI quan sát StateFlow trong Kotlin.

### BlocListener

Nhiệm vụ: xử lý side effect.

Ví dụ:
- Navigate.
- Hiện SnackBar.
- Hiện Dialog.
- Hiện Toast.

Người học từng nhầm rằng BlocListener cũng là thành phần cần thiết để render UI.

Đã làm rõ:

BlocListener không có nhiệm vụ render UI. Nó dùng để thực hiện những hành động phát sinh khi State thay đổi.

### BlocConsumer

Kết hợp hai chức năng:
- BlocBuilder.
- BlocListener.

Sử dụng khi một khu vực cần vừa render UI vừa xử lý side effect.

## 3.4. listenWhen và buildWhen

Đã tiếp cận cơ chế lọc State:

- `buildWhen`: quyết định khi nào BlocBuilder cần rebuild.
- `listenWhen`: quyết định khi nào BlocListener thực hiện callback.

Mục đích là tránh rebuild hoặc xử lý side effect không cần thiết.

## 3.5. One-time Event và UiEffect

Đã thảo luận một nguyên tắc quan trọng:

State nên chứa dữ liệu phục vụ render UI.

Không nên đưa những hành động chỉ xảy ra một lần như:
- Navigate.
- Hiện thông báo.
- Mở Dialog.

vào State theo cách khiến chúng có thể bị thực hiện lại khi UI nhận State cũ.

Người học từng lựa chọn hướng Production Concept - Minimal Implementation:

- State chứa dữ liệu hiển thị.
- UiEffect đại diện cho hành động một lần.
- Không thêm quá nhiều abstraction khi chưa cần thiết.

Đây là một nguyên tắc cần được duy trì khi hướng dẫn tiếp.

## 3.6. BaseBloc, CommonBloc và AppBloc

Người học đã tìm hiểu kiến trúc BLoC có nhiều cấp độ.

### BaseBloc

- Là nền tảng kỹ thuật dùng chung.
- Chuẩn hóa những thành phần và hành vi chung.
- Không phải một State Manager dùng để quản lý tất cả State của ứng dụng.

### CommonBloc

Đã được thảo luận như một BLoC phục vụ hạ tầng UI ở phạm vi màn hình.

Các chức năng được đề cập:
- Loading.
- Error.
- Force logout.
- Quản lý loadingCount.

### AppBloc

Được thảo luận như một BLoC cấp ứng dụng.

Ví dụ:
- isInitialized.
- isLoggedIn.
- Kiểm tra trạng thái đăng nhập thông qua IsLoggedInUseCase.

Đã làm rõ:
- AppBloc và CommonBloc có phạm vi trách nhiệm khác nhau.
- Cả hai có thể kế thừa BaseBloc.
- Không nên hiểu CommonBloc là class cha quản lý AppBloc.

## 3.7. EventTransformer

Đã từng tìm hiểu cơ chế xử lý EventTransformer.

Các khái niệm được đề cập:

- log()
- flatMap()
- debounceTime()
- throttleTime()
- distinct()

Đã được giải thích:
- Transformer can thiệp vào luồng Event.
- Handler thực hiện nghiệp vụ khi nhận Event.
- Transformer không phải là nơi thay thế handler.

## 3.8. Bloc-to-Bloc Communication

Đã tiếp cận vấn đề giao tiếp giữa các BLoC.

Ví dụ:

AuthBloc logout → CartBloc cần xóa giỏ hàng.

Các cách đã được thảo luận:

1. UI lắng nghe Bloc A rồi gửi Event sang Bloc B.
2. Inject Bloc A vào Bloc B và lắng nghe stream.
3. Giao tiếp gián tiếp qua Repository hoặc UseCase dùng chung.

Đây là phần cần tiếp tục củng cố khi học các ứng dụng nhiều feature.

# PHẦN 4. CLEAN ARCHITECTURE

Người học đã tiếp cận Clean Architecture theo hướng phân chia rõ ba tầng.

## 4.1. Presentation

Bao gồm:
- Screen.
- Widget.
- BLoC.
- Event.
- State.

Chịu trách nhiệm hiển thị UI và điều phối tương tác người dùng.

## 4.2. Domain

Bao gồm:
- Entity.
- Repository Interface.
- UseCase.

Đây là tầng chứa nghiệp vụ và hợp đồng mà các tầng khác phải tuân thủ.

## 4.3. Data

Bao gồm:
- DTO.
- Mapper.
- DataSource.
- Repository Implementation.
- API hoặc Local Database.

Đây là tầng triển khai việc lấy, lưu trữ và chuyển đổi dữ liệu.

## 4.4. Repository Interface và Repository Implementation

Đã tìm hiểu nguyên tắc:

Repository Interface nằm ở Domain.

Repository Implementation nằm ở Data.

Ví dụ:

```dart
abstract class UserRepository {
  Future<UserEntity> getUser();
}
```

Implementation:

```dart
class UserRepositoryImpl implements UserRepository {
  // Triển khai việc lấy dữ liệu
}
```

Đã hiểu Repository Implementation không đơn thuần chỉ là class gọi API.

Nó đóng vai trò trung gian, che giấu cách lấy dữ liệu thực tế với Domain và Presentation.

## 4.5. DTO → Entity và Mapper

Đây là một chủ đề đã được thảo luận thông qua ví dụ Supabase.

Luồng dữ liệu:

Entity → Mapper → Map payload → Supabase

Supabase → Raw Map → DTO → Mapper → Entity

Đã hiểu:
- DTO đại diện cho cấu trúc dữ liệu giao tiếp với nguồn dữ liệu.
- Entity đại diện cho dữ liệu nghiệp vụ trong Domain.
- Mapper chịu trách nhiệm chuyển đổi giữa hai cấu trúc.
- Không nên để Domain phụ thuộc vào tên trường hoặc định dạng riêng của Supabase.

Ví dụ:

```dart
// Domain
class UserEntity {
  final String userId;

  UserEntity({required this.userId});
}
```

Backend có thể sử dụng `user_id`, trong khi Domain sử dụng `userId`.

Mapper chịu trách nhiệm chuyển đổi hai cách đặt tên này.

## 4.6. BaseUseCase và BaseMapper

Đã tìm hiểu lý do một số dự án tạo các class nền tảng.

Đã được giải thích:

- BaseUseCase giúp chuẩn hóa cách gọi UseCase.
- BaseMapper giúp chuẩn hóa cách chuyển đổi dữ liệu.
- Có thể chứa logic dùng chung khi thực sự cần thiết.
- Không phải mọi class đều cần kế thừa Base.

Ví dụ:
- Entity không nhất thiết cần BaseEntity.
- DTO không nhất thiết cần BaseDTO.
- Repository Interface không nhất thiết cần BaseRepository.

Người học từng thắc mắc rằng BaseInput không có logic thì tại sao phải tồn tại.

Nguyên tắc đã được làm rõ: một Base class đôi khi chỉ đóng vai trò contract/type constraint để đảm bảo các class tuân theo cùng một quy ước. Không phải Base class nào cũng bắt buộc chứa logic xử lý.

## 4.7. Input và Output của UseCase

Đã tìm hiểu Input và Output thông qua ví dụ:

```dart
Future<Output> call(Input input);
```

Đã hiểu:

- Input là dữ liệu nghiệp vụ mà UseCase cần nhận.
- Output là kết quả nghiệp vụ mà UseCase trả về.
- Repository có thể trả về Entity.
- UseCase sử dụng Entity đó để thực hiện nghiệp vụ hoặc tạo Output phù hợp.

Ví dụ đã thảo luận:

AddressEntity được sử dụng làm dữ liệu đầu vào trong một UseCase.

Cần tiếp tục củng cố sự khác nhau giữa:
- Input của UseCase.
- Request DTO.
- Entity.
- Output của UseCase.
- Response DTO.

# PHẦN 5. ASYNC, FUTURE VÀ XỬ LÝ DỮ LIỆU

## 5.1. Future

Đã gặp và thảo luận các kiểu:

```dart
Future<void>
Future<T>
Future<T?>
```

Đã làm rõ:
- Future biểu diễn một kết quả có thể nhận được trong tương lai.
- `void` biểu thị không có giá trị trả về cần sử dụng.
- `T` là kiểu dữ liệu kết quả.
- `T?` cho phép kết quả có thể null.

Cần tiếp tục củng cố async/await, Future chaining và cách xử lý lỗi bất đồng bộ.

## 5.2. Type casting với as

Đã thảo luận trực tiếp dòng code:

```dart
return CartItemResponseDto.fromJson(
  response as Map<String, dynamic>,
);
```

Người học thắc mắc vì sao phải có `as` ở đây nhưng một số đoạn code khác lại không cần.

Đã làm rõ hai công việc khác nhau:

**as**
- Xác nhận/cast kiểu dữ liệu.
- Không tự chuyển một Map thành DTO.
- Có thể phát sinh lỗi nếu kiểu thực tế không phù hợp.

**fromJson**
- Nhận dữ liệu Map.
- Tạo object DTO từ dữ liệu đó.

Ví dụ:

```dart
final map = response as Map<String, dynamic>;

final dto = CartItemResponseDto.fromJson(map);
```

Đây là một điểm người học đã hiểu về sự khác nhau giữa kiểu dữ liệu runtime và việc khởi tạo model.

# PHẦN 6. DEPENDENCY INJECTION — GET_IT VÀ INJECTABLE

Người học đã tìm hiểu hệ thống DI trong Flutter.

## 6.1. GetIt

Đã tiếp cận GetIt như một Service Locator.

Các khái niệm:
- registerFactory.
- registerLazySingleton.
- registerSingleton.
- get<T>().

Mục đích:
- Đăng ký dependency.
- Quản lý cách tạo object.
- Lấy dependency đã đăng ký.
- Kết nối BLoC → UseCase → Repository.

## 6.2. Injectable

Đã tìm hiểu Injectable là công cụ tự động hóa việc đăng ký dependency thông qua annotation và code generation.

Ví dụ:

```dart
@injectable
class GetProductsUseCase {
  // ...
}
```

Đã tìm hiểu sự khác nhau giữa:
- GetIt: cơ chế Service Locator.
- Injectable: công cụ hỗ trợ sinh code đăng ký dependency cho GetIt.

## 6.3. di.config.dart

Đã hỏi tại sao file `di.config.dart` tự động xuất hiện những đoạn code như:

```dart
gh.factory<_i756.GetFeaturedProductsUseCase>(
  () => _i756.GetFeaturedProductsUseCase(
    gh<_i494.ProductRepository>(),
  ),
);
```

Đã làm rõ:

- Đây là code được generate.
- `gh.factory` đăng ký một dependency với GetIt.
- Hàm callback mô tả cách tạo object.
- `gh<_i494.ProductRepository>()` lấy Repository đã được đăng ký.
- UseCase được tạo với Repository thông qua constructor injection.

Người học đã hiểu rằng không cần tự viết những dòng đăng ký tương tự nếu đang sử dụng Injectable và chạy code generation đúng cách.

# PHẦN 7. FIREBASE VÀ SUPABASE

## 7.1. Supabase

Đã có những cuộc thảo luận thực tế về việc sử dụng Supabase trong Clean Architecture.

Các nội dung:
- Gọi Supabase từ Data Layer.
- Repository Implementation.
- DTO.
- Entity.
- Mapper.
- Map<String, dynamic>.
- fromJson().
- Type casting bằng as.
- UseCase Input/Output.

Đặc biệt đã phân tích một ví dụ cập nhật số lượng sản phẩm trong giỏ hàng:


# PHẦN 8. CẤU TRÚC THƯ MỤC FLUTTER ĐÃ ĐỊNH HƯỚNG

Người học đã xây dựng một cấu trúc Flutter theo hướng Clean Architecture, chia theo các tầng:

```text
lib/
├── core/

│
├── data/
│   ├── local/
│   │   ├── database/
│   │   ├── datasources/
│   │   └── models/
│   │
│   ├── remote/
│   │   ├── datasources/
│   │   └── models/
│   │       ├── requests/
│   │       └── responses/
```

Định hướng trách nhiệm:

- domain: nghiệp vụ và abstraction.
- feature: tổ chức các màn hình và nghiệp vụ theo chức năng.
- app.dart: khởi tạo ứng dụng, DI, Theme, Router.
- main.dart: entry point.

Đây là cấu trúc kiến trúc đã được lưu thành tài liệu riêng.

## Giai đoạn 2 — Production và tối ưu hóa

Chỉ nâng cấp khi người học chủ động phát tín hiệu như:

- "Mở khóa nâng cao".
- "Dùng thư viện".
- "Production style".
- "Tôi đã hiểu bản chất rồi".

Khi đó cần:
1. Xác nhận chuyển giai đoạn.
2. Giải thích thư viện mới giải quyết vấn đề gì.
3. Chỉ ra phần code thủ công trước đây được tự động hóa như thế nào.
4. Áp dụng chuẩn mới trong các bài học tiếp theo.

Nếu người học yêu cầu một thư viện mới nhưng không phát tín hiệu nâng cấp rõ ràng, cần hỏi:

"Bạn muốn nâng cấp khóa học sang Giai đoạn 2, hay chỉ muốn sửa đoạn code này mà vẫn giữ chuẩn Giai đoạn 1?"

Nếu người học yêu cầu quay lại cách học cơ bản, phải lập tức quay về Giai đoạn 1.

**Meta Rule:** Công cụ và thư viện phục vụ mục tiêu học tập. Không được dùng quy tắc cũ để cản trở việc nâng cấp khi người học đã chủ động thay đổi mục tiêu.

| Drift | Room |
| Hive | Lưu trữ key-value/object |

Không phải lúc nào cũng cần so sánh với Android. Chỉ sử dụng khi nó giúp làm sáng tỏ vấn đề.
