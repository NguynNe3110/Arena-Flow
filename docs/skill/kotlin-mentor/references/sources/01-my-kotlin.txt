# HỒ SƠ KIẾN THỨC KOTLIN & ANDROID NATIVE

## 1. Mục đích tài liệu

Tài liệu này tổng hợp kiến thức lập trình Kotlin và Android Native mà người học đã từng tìm hiểu, thảo luận và xây dựng định hướng học tập cùng ChatGPT trước đây.

Mục tiêu là cung cấp cho AI mới một bức tranh tương đối đầy đủ về nền tảng hiện tại, tránh:
- Giải thích lại những kiến thức đã hiểu mà không cần thiết.
- Đánh giá người học là người mới hoàn toàn.

- Thay đổi kiến trúc và phong cách code liên tục giữa các ví dụ.

Lưu ý: Các mục dưới đây được phân loại theo mức độ đã thảo luận, đã thể hiện hiểu biết hoặc mới nằm trong kế hoạch. Không được mặc định rằng người học đã thành thạo tất cả.

# PHẦN I. NỀN TẢNG NGÔN NGỮ KOTLIN

## 2. Biến và tính bất biến

Các khái niệm đã được đưa vào quá trình học:

- `val`: Khai báo biến không thể gán lại.
- `var`: Khai báo biến có thể thay đổi giá trị.
- `const val`: Hằng số compile-time, dùng trong những trường hợp phù hợp.
- Phân biệt giữa khả năng gán lại biến và khả năng thay đổi trạng thái của object.

Định hướng tư duy:
- Ưu tiên `val` khi không cần gán lại.
- Chỉ dùng `var` khi thực sự cần thay đổi.
- Không nhầm lẫn `val` với việc object bên trong chắc chắn bất biến.

Mức độ: Đã tiếp xúc với nền tảng này trong quá trình học Kotlin và Android.

## 3. Data Class

Đã tìm hiểu về `data class`, đặc biệt trong việc xây dựng model cho ứng dụng Android.

Ví dụ:

```kotlin
data class Ticket(
    val id: Int,
    val title: String,
    val description: String? = null
)
```

Các nội dung đã tiếp xúc:
- Khai báo data class.
- Primary constructor.
- Khai báo thuộc tính bằng `val` và `var`.
- Giá trị mặc định trong constructor.
- Thuộc tính nullable.
- Cho phép bỏ qua tham số có giá trị mặc định khi khởi tạo object.
- Vai trò của data class trong việc biểu diễn dữ liệu.

Đã gặp các hàm được compiler tự sinh như:
- `copy()`
- `equals()`
- `hashCode()`
- `toString()`
- `componentN()`

Ví dụ sử dụng:

```kotlin
val updatedTicket = ticket.copy(
    title = "New title"
)
```

Ứng dụng thực tế:
- Model dữ liệu.
- UI State.
- API DTO.
- Domain Model.
- Navigation arguments/configuration.

## 4. Null Safety

Đây là một trong những chủ đề đã được tìm hiểu trong quá trình học.

Đã tiếp xúc với:

```kotlin
String
String?
```

Phân biệt:
- `String`: Không cho phép null.
- `String?`: Có thể chứa null.

Các toán tử và cách xử lý:

```kotlin
?.   // Safe call
!!   // Not-null assertion
?:   // Elvis operator
```

Đã tìm hiểu cách sử dụng:

```kotlin
user?.name
```

```kotlin
val name = user?.name ?: "Unknown"
```

```kotlin
user?.let {
    println(it.name)
}
```

Các nội dung cần AI tiếp tục kiểm tra mức độ hiểu:
- Smart cast.
- Safe cast `as?`.
- `requireNotNull()`.
- Phân biệt nullability ở compile-time và lỗi runtime.
- Khi nào nên dùng `let` để xử lý nullable.
- Vì sao lạm dụng `!!` là không tốt.

Lưu ý: Người học cũng đã từng học null safety trong Dart. Không được mặc định kiến thức Dart đồng nghĩa với việc đã nắm vững toàn bộ cơ chế null safety của Kotlin.

## 5. Imports và Package

Đã thảo luận về cách tổ chức và sử dụng import trong Kotlin.

Các nội dung:
- Import class từ package khác.
- Wildcard import (`*`).
- Trường hợp các class cùng package không cần import.
- Import alias để tránh trùng tên.
- Phân biệt import trong Kotlin với dependency trong Gradle.
- Kotlin không sử dụng cơ chế export barrel như một số ngôn ngữ khác.

Ví dụ:

```kotlin
import android.os.Parcelable
import kotlinx.parcelize.Parcelize
```

## 6. Annotation và Resource trong Android

Đã tìm hiểu cách Kotlin sử dụng annotation để xác định loại tài nguyên Android.

Đã tiếp xúc với:

```kotlin
@StringRes
@DrawableRes
```

Ví dụ model:

```kotlin
data class NavigationBarItem(
    @StringRes val titleRes: Int,
    @DrawableRes val iconRes: Int,
    val route: NavigationRoute
)
```

Đã hiểu các điểm quan trọng:
- Resource ID của Android vẫn là kiểu `Int`.
- `@StringRes` đánh dấu một Int được kỳ vọng là String resource.
- `@DrawableRes` đánh dấu một Int được kỳ vọng là Drawable resource.
- Annotation hỗ trợ Lint kiểm tra việc sử dụng sai loại tài nguyên.

Đã tìm hiểu cách sử dụng trong Compose:

```kotlin
stringResource(item.titleRes)
```

```kotlin
painterResource(item.iconRes)
```

Đã phân biệt các kiểu biểu diễn icon/image:
- Drawable hoặc mipmap resource: `Int`.
- Material Compose icon: `ImageVector`.
- Đường dẫn ảnh hoặc URI: `String` hoặc `Uri`.
- Đối tượng hiển thị hình ảnh: `Drawable` hoặc `Painter`.

## 7. Parcelable và Parcelize

Đã trực tiếp thảo luận về `@Parcelize` và `Parcelable`.

Mục đích:
- Cho phép truyền dữ liệu giữa các thành phần Android.
- Truyền object thông qua Intent hoặc Bundle.
- Sử dụng model Kotlin làm dữ liệu truyền giữa các màn hình.

Ví dụ:

```kotlin
@Parcelize
data class Ticket(
    val id: Int,
    val title: String
) : Parcelable
```

Đã tiếp xúc với:
- Interface `Parcelable`.
- Annotation `@Parcelize`.
- Plugin Kotlin Parcelize.
- Mối liên hệ giữa model và Intent/Bundle.

# PHẦN III. KOTLIN TRONG ANDROID ARCHITECTURE

## 10. Tư duy Activity không nên chứa toàn bộ logic

Đây là một trong những chủ đề quan trọng trong quá trình học Android.

Người học đã đi qua tư duy:

- Activity chịu trách nhiệm quản lý giao diện và tương tác với hệ thống Android.
- Không nên đưa toàn bộ business logic vào Activity.
- Không nên để Activity trở thành nơi lưu trữ và quản lý toàn bộ dữ liệu của ứng dụng.
- Cần phân tách UI, state và business logic.
- ViewModel xuất hiện để quản lý UI-related state và logic phù hợp với vòng đời Android.

Đã xây dựng định hướng học từ:

Activity → State → ViewModel → LiveData → StateFlow → Compose.

## 11. MVVM

Đây là một trong những phần người học đã tìm hiểu tương đối nhiều.

Mô hình tư duy MVVM hiện tại:

```text
       UI (Activity / Fragment)
                 |
                 | User Action
                 v
             ViewModel
                 |
                 | Business Logic
                 v
             Repository
                 |
          +------+------+
          |             |
       Remote         Local
        API           Room
```

Trách nhiệm từng thành phần:

**View**
- Hiển thị giao diện.
- Nhận tương tác người dùng.
- Gửi action/event đến ViewModel.
- Quan sát state để cập nhật giao diện.

**ViewModel**
- Quản lý UI State.
- Xử lý logic phù hợp với presentation layer.
- Tiếp nhận action từ UI.
- Gọi Repository hoặc UseCase.
- Expose StateFlow cho UI quan sát.

**Repository**
- Là lớp trung gian quản lý nguồn dữ liệu.
- Không để ViewModel phụ thuộc trực tiếp vào API hoặc Database.
- Có thể kết hợp Remote và Local Data Source.

Người học đã thể hiện cách hiểu:

- UI gửi sự kiện xuống ViewModel.
- ViewModel xử lý và cập nhật StateFlow.
- UI quan sát StateFlow và tự cập nhật khi state thay đổi.

Đây là nền tảng kiến trúc cần được giữ xuyên suốt trong những bài học tiếp theo.

## 12. LiveData và StateFlow

Đã học và thảo luận về sự khác nhau giữa LiveData và StateFlow.

Các chủ đề:

- LiveData là observable holder trong Android.
- StateFlow thuộc Kotlin Coroutines.
- `MutableStateFlow` dùng để cập nhật state.
- `StateFlow` được expose ra ngoài dưới dạng read-only.
- UI collect state để render.
- StateFlow phù hợp với tư duy quản lý business/UI state hiện đại.

Ví dụ:

```kotlin
private val _uiState = MutableStateFlow(
    HomeUiState()
)

val uiState: StateFlow<HomeUiState> = _uiState
```

Cập nhật state:

```kotlin
_uiState.update { currentState ->
    currentState.copy(
        isLoading = true
    )
}
```

Đã tìm hiểu:
- Vì sao không nên để UI trực tiếp sửa state nội bộ của ViewModel.
- Vì sao nên expose StateFlow thay vì MutableStateFlow.
- Vì sao nên gom state vào một UiState.
- Khái niệm Single Source of Truth.

## 13. UiState

Đã học về việc gom trạng thái của một màn hình vào một đối tượng UiState.

Ví dụ:

```kotlin
data class HomeUiState(
    val isLoading: Boolean = false,
    val users: List<User> = emptyList(),
    val error: String? = null
)
```

Thay vì tạo nhiều state riêng lẻ, ViewModel có thể expose một state thống nhất.

Mục tiêu:
- Dễ quản lý.
- Dễ theo dõi.
- Giảm sự phân tán state.
- UI có một nguồn dữ liệu thống nhất.
- Dễ kiểm soát các trạng thái loading, success và error.

## 14. Event và State

Đây là chủ đề người học đã dành thời gian tìm hiểu.

Phân biệt:

**State**
- Đại diện cho trạng thái hiện tại của màn hình.
- Có thể được quan sát và render nhiều lần.
- Ví dụ: danh sách người dùng, loading, nội dung màn hình.

**Event**
- Đại diện cho một hành động hoặc sự kiện.
- Ví dụ: click button, submit form.

**One-time UI Event**
- Ví dụ: Snackbar, Toast, Navigate.
- Không nên xử lý như một state thông thường nếu việc phát lại sự kiện gây ra hành vi không mong muốn.

Đã tiếp cận các công cụ:
- StateFlow cho state.
- SharedFlow cho event.
- Event handling trong ViewModel.

Tư duy cần giữ:
State và Event có mục đích khác nhau, không nên gộp tất cả vào một luồng dữ liệu mà không phân biệt ngữ nghĩa.

## 15. MVVM và MVI

Người học đã tìm hiểu MVVM và bắt đầu tìm hiểu MVI.

Cách hiểu MVVM hiện tại:
- Event đi vào ViewModel.
- ViewModel xử lý.
- State được expose qua StateFlow.
- UI quan sát state.

Định hướng học MVI:
- Action/Intent đại diện cho hành động.
- Reducer hoặc logic xử lý chuyển state.
- State là trạng thái hiện tại của màn hình.
- Luồng dữ liệu có tính một chiều.

Người học muốn hiểu rõ sự khác biệt giữa MVVM và MVI, không muốn chỉ đổi tên các thành phần mà không hiểu bản chất.

Chưa nên mặc định đã thành thạo MVI hoặc reducer pattern.

# PHẦN IV. COROUTINES VÀ FLOW

## 16. Kotlin Coroutines

Coroutines đã được đưa vào chương trình học Android, đặc biệt khi làm việc với API, Room và Firebase.

Các khái niệm đã được xác định là cần học:

- `suspend` function.
- `launch`.
- `async`.
- `withContext`.
- Dispatchers.
- Structured concurrency.
- Exception handling.

Mục tiêu:
- Xử lý tác vụ bất đồng bộ.
- Không thực hiện I/O hoặc network operation trên Main Thread.
- Quản lý vòng đời tác vụ.
- Kết hợp API và Database với ViewModel.

## 17. Dispatchers và Thread

Đã xác định đây là phần cần hiểu khi học Coroutine.

Các Dispatcher:

```kotlin
Dispatchers.Main
Dispatchers.IO
Dispatchers.Default
```

Định hướng:
- Main: Công việc liên quan đến UI.
- IO: I/O, đọc ghi dữ liệu, network.
- Default: Công việc tính toán CPU-intensive.

Cần phân biệt:
- Thread.
- Coroutine.
- Dispatcher.
- Suspend function.

Không được đồng nhất Coroutine với Thread.

## 18. Flow, StateFlow và SharedFlow

Các nội dung đã được đưa vào quá trình học:

- Flow là asynchronous data stream.
- StateFlow là state holder có giá trị hiện tại.
- SharedFlow là hot flow có khả năng phát dữ liệu cho nhiều collector.
- Collect Flow trong ViewModel.
- Kết hợp Flow từ Room.
- Chuyển đổi callback sang suspend hoặc Flow khi tích hợp Firebase.

Mục tiêu ứng dụng:

```kotlin
fun getUsers(): Flow<List<User>>
```

Kết hợp với ViewModel để UI nhận được dữ liệu mới khi Database thay đổi.

## 23. Data Synchronization và Cache

Đã thảo luận ba cách quản lý dữ liệu giữa API và Database:

**Kiểu A – Manual Refresh**
- Khi mở app chỉ observe Database.
- Khi người dùng bấm Refresh mới gọi API.

**Kiểu B – Auto Refresh**
- Khi mở màn hình, nếu Database trống thì gọi API.
- Nếu đã có dữ liệu thì hiển thị trước, có thể refresh ngầm.

**Kiểu C – Cache TTL**
- Lưu thời điểm fetch dữ liệu.
- Nếu dữ liệu quá thời hạn thì gọi API.
- Nếu chưa quá thời hạn thì sử dụng cache.

Định hướng học:
A → B → C.

## 34. Luôn giải thích cấu trúc trước khi viết code

Khi giới thiệu một chủ đề mới, nên đi theo thứ tự:

1. Vấn đề thực tế đang gặp phải là gì?
2. Vì sao cần khái niệm này?
3. Nó giải quyết vấn đề nào?
4. Nó nằm ở đâu trong kiến trúc?
5. Các thành phần liên quan với nhau thế nào?
6. Sau đó mới đi vào code.
7. Giải thích từng phần quan trọng trong code.
8. Kết thúc bằng luồng hoạt động tổng thể.

Ví dụ khi dạy Repository:

Không nên bắt đầu ngay bằng một đoạn code Repository dài.

Nên giải thích trước:
- Nếu ViewModel gọi API trực tiếp thì có vấn đề gì?
- Repository xuất hiện để giải quyết điều gì?
- Repository interface nằm ở đâu?
- Repository implementation nằm ở đâu?
- API và Database được kết nối thế nào?

Sau đó mới xây dựng code.
